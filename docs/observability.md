# Диагностика ChronoCampus

Администратор видит новый раздел **«Диагностика»**. На странице **«Генератор»** у выбранного черновика есть текущий запуск и история расчётов. Эти функции работают без Docker, Grafana и внешних сервисов.

## Как найти проблему

1. При ошибке API интерфейс показывает **код запроса**. Скопируйте его в фильтр «Код запроса» на вкладке «События». Код генерирует сервер; присланный клиентом `X-Request-ID` не используется.
2. Откройте подробности события: маршрут без конкретных значений, HTTP-статус, время ответа, код отказа либо тип исключения и безопасные кадры стека. У кадров есть файл, функция и строка; текст исключения, исходный код и локальные переменные не записываются.
3. Если проблема в расписании, откройте запуск по номеру. Там указаны алгоритм, seed, черновик, автор, ревизия, отпечаток входных данных, время ожидания, длительность, этапы, размещённые занятия, причины пропусков и показатели качества.
4. Если перед ошибкой меняли правила, откройте «Изменения и действия». Фильтры по пользователю ID, разделу и коду запроса помогают связать изменение с запросом и запуском.
5. «Запросы API» показывает количество, среднее и максимальное время ответа отдельно по методу, шаблону маршрута и статусу. Карточки сверху показывают готовность БД и схемы, память процесса, накопленное время CPU, SQL-запросы, ошибки записи логов, очередь и работающие расчёты.

Раздел доступен только администраторам. Обновление происходит каждые четыре секунды; его можно выключить. Карточка текущей генерации запрашивается раз в полторы секунды. При ошибке опрос повторяется, а последние полученные данные помечаются как устаревшие. Переключение черновика отменяет применение устаревших ответов к новому выбору.

## Что означает история генерации

Сохраняются **реальные этапы**, а не расчётный процент готовности: подготовка, построение кандидатов, начальное решение, модель, цели CP-SAT, проверка и сохранение. Обновления прогресса ограничены одним в секунду на одном этапе; переходы этапов сохраняются сразу. Таймлайн хранит последние 60 переходов. Во время этапа без нового решения поле «Обновлено» может не изменяться: это само по себе не доказывает зависание.

| Статус | Значение |
| --- | --- |
| `queued` / `running` | Ожидание единственного рабочего потока / расчёт. |
| `complete` | Независимая проверка подтвердила полное расписание. Это ещё не публикация. |
| `partial` | Размещена только часть занятий; причины доступны в отчёте. |
| `rejected` | Результат отклонён проверкой или некорректными закреплениями. |
| `stale` | Пока шёл расчёт, изменились входные данные или черновик; результат не применён. |
| `failed` | Исключение либо невозможность поставить задачу в очередь. |
| `interrupted` | После перезапуска сервера обнаружена незавершённая задача. Нужен новый запуск. |

Статус решения CP-SAT показывается отдельно. `FEASIBLE` означает найденное допустимое решение, но не доказанную оптимальность; `OPTIMAL` относится к соответствующей фазе модели. Эвристический алгоритм не доказывает оптимальность. Показатели качества и полнота расписания — разные характеристики.

В истории можно отметить два завершившихся запуска и сравнить результаты. Сравнение имеет смысл при одинаковых правилах, нагрузках, закреплениях, внешнем расписании и бюджете поиска. `comparison_hash` исключает служебную ревизию и идентификаторы копий назначений, сохраняя содержательные входы. При разных или отсутствующих отпечатках интерфейс предупреждает. Полный `input_hash` сохраняется отдельно для воспроизводимости. Старые запуски не получают выдуманный прогресс, автора или длительность ожидания; отсутствующие сведения показываются как «—».

История API не возвращает тяжёлый снимок входных данных или весь список назначений. Подробный отчёт содержит причины, метрики и фазы решения. Снимок остаётся в БД для воспроизведения.

## Логи, аудит и защита данных

| Данные | Хранение и срок |
| --- | --- |
| Последние события в интерфейсе | Кольцевой буфер на 2000 записей текущего процесса. Есть счётчик вытесненных событий. |
| JSON-логи | `backend/.logs/events.jsonl` и пять архивов, по умолчанию до 5 MB каждый; ротация по размеру. |
| HTTP/SQL-метрики | Память текущего процесса; сбрасываются при перезапуске. |
| Запуски, прогресс, аудит | SQL Server; переживают перезапуск. Автоматического удаления пока нет. |
| Метрики Prometheus, если включён | Отдельный Docker volume; ограничение 14 дней и 1 GB. |

Настройки `DIAGNOSTIC_LOG_DIRECTORY`, `DIAGNOSTIC_LOG_MAX_BYTES`, `DIAGNOSTIC_LOG_BACKUPS` переопределяют каталог и ротацию. `DIAGNOSTIC_DEBUG=true` добавляет успешные запросы опроса диагностики; обычно они учитываются только в метриках, чтобы журнал не заполнялся служебными событиями. Изменения настроек требуют перезапуска API.

Пример чтения текущего файла из корня проекта в PowerShell:

```powershell
Get-Content backend/.logs/events.jsonl -Tail 30 -Wait
```

Пароли, хеши паролей, cookies, заголовки авторизации, CSRF и reset-токены, тела запросов, SQL-текст/параметры, заметки и переписка не добавляются в диагностические записи. События API используют шаблоны маршрутов вместо URL с параметрами. Стандартный access-log Uvicorn отключён, поскольку он может содержать query string.

Аудит записывается в **одной транзакции с изменением**: откат операции откатывает и запись об успехе. Он охватывает справочники и правила, создание черновика, запуск генерации, перемещения/отмены, публикацию, вход/выход, изменения пароля и статусы обращений. Различия «до/после» сохраняются только для разрешённых технических полей. Имена, адреса, названия и свободный текст исключаются; поэтому некоторые действия имеют пустое описание изменений, но сохраняют действие, автора, объект и время. Аудит не является защищённым от изменений внешним архивом.

Ошибки браузера отправляются только из авторизованной сессии: категория, раздел, известный модуль/номер строки и связанный код API-запроса, когда он доступен. Нет исходного сообщения, полного стека или URL. Лимиты: не чаще одного отчёта в пять секунд в браузере и десяти за минуту на аккаунт в API. При отключённой сети доставка не гарантируется; постоянная очередь браузерных ошибок отсутствует. В production координаты собранного bundle требуют соответствующего build-артефакта для разбора.

Ошибка записи диагностического файла или промежуточного прогресса не должна прерывать обычную операцию или сам поиск. Такие ошибки учитываются отдельно. Аудит и итоговый результат требуют доступной БД: при потере соединения операция может завершиться ошибкой. Если сервер не смог сохранить итог сбоя, событие `generation.failure_persistence_failed` остаётся в доступном журнале, а незавершённая задача при следующем старте помечается `interrupted`.

## Проверки готовности и метрики

- `GET /api/health` — процесс отвечает; не проверяет БД.
- `GET /api/ready` — соединение с БД, нужные столбцы миграции `0003_observability`, таблица аудита и строка ревизии доступны; ответ 200 или 503 без внутренних подробностей.
- `GET /api/admin/diagnostics/system`, `/events`, `/requests`, `/audit` — административная диагностика.
- `GET /api/admin/schedule/runs` — история с пагинацией и фильтрами; `/runs/{id}` — подробности.
- `GET /api/admin/diagnostics/metrics` — формат Prometheus, с административной сессией либо отдельным Bearer-токеном.

Токен метрик задаётся через `METRICS_TOKEN_FILE` или `METRICS_TOKEN` и действует **только** на endpoint метрик. Предпочтителен файл вне Git. Нет доступа к журналам, пользовательским данным и изменению расписания через этот токен. Метрики включают HTTP-гистограмму, время CPU, память, счётчики SQL/ошибок логов, готовность БД и количество запусков каждого статуса. User ID, request ID, run ID и произвольные URL не становятся labels. Длительность SQL измеряется по выполнению cursor; она не является временем всей транзакции или всех ожиданий пула.

## Дополнительные Grafana и Prometheus

Файлы находятся в `monitoring/`. [Prometheus](https://prometheus.io/docs/introduction/overview/) собирает метрики; [Grafana](https://grafana.com/docs/grafana/latest/administration/provisioning/) получает заранее настроенный источник и dashboard. Здесь они не хранят журнал событий. Loki и OpenTelemetry tracing в эту реализацию не добавлены.

При установленном Docker Desktop выполните из корня проекта:

```powershell
powershell -ExecutionPolicy Bypass -File monitoring/setup.ps1
# Перезапустите backend, чтобы он прочитал METRICS_TOKEN_FILE.
docker compose -f monitoring/compose.yaml config --quiet
docker compose -f monitoring/compose.yaml up -d
```

Скрипт создаёт случайные секреты в игнорируемом `monitoring/secrets/` и добавляет путь токена в `backend/.env`, если настройки ещё нет. Существующие секреты не перезаписываются. Если `METRICS_TOKEN_FILE` уже настроен на другой файл, укажите тот же файл в секции `secrets.metrics_token.file` Compose. Файлы секретов остаются обычными локальными файлами: доступ к каталогу нужно ограничить средствами ОС.

Prometheus обращается к `host.docker.internal:8000`. Backend должен быть доступен из Docker-сети: слушающий только `127.0.0.1` процесс может быть недоступен. При необходимости используйте адрес сетевого интерфейса, доступного Docker, или `--host 0.0.0.0` с правилами брандмауэра, разрешающими только необходимое подключение. Текущий штатный локальный запуск продолжает использовать `127.0.0.1`.

- Prometheus: `http://localhost:9090`; проверьте Targets и Alerts.
- Grafana: `http://localhost:3001`; пользователь `admin`, пароль в `monitoring/secrets/grafana_password`.
- Dashboard **ChronoCampus — Operations**: API/БД, частота запросов, ошибки, p95, статусы генерации, память, CPU и SQL.
- Тревоги: недоступность API/БД, рост 5xx, ошибки логов, новые failed/rejected/interrupted-запуски, p95 API выше двух секунд, непустая очередь дольше трёх минут. Последние два сигнала требуют проверки нагрузки и не доказывают зависание. Тревоги видны в Prometheus. Alertmanager, отправка почты/Slack и внешние получатели не настроены.

Порты мониторинга опубликованы только на loopback. Сервисы опциональны; остановить их без удаления накопленных данных можно через `docker compose -f monitoring/compose.yaml down`.

## Границы и обслуживание

Поддерживается один API-процесс и один поток генерации. Несколько workers потребуют общей очереди, распределённой корреляции и общего хранилища событий. Это не распределённая трассировка. Сбой всего компьютера или диска не гарантирует доставку последних записей; внешний мониторинг нужен для наблюдения за отключённым процессом.

Текущая readiness-проверка проверяет необходимые элементы схемы, но не доказывает корректность каждого справочника, целостность всей БД или качество расписания. Для этого остаются доменный валидатор, тесты и резервное копирование. Наблюдаемость помогает находить и объяснять проблемы, но не гарантирует обнаружение каждой ошибки.

Запуски и аудит сохраняются без автоматической очистки: контролируйте рост БД и согласуйте архивирование/сроки хранения перед длительной эксплуатацией. Сохраняйте резервные копии. Миграция добавочная; downgrade не удаляет историю, а требует восстановления резервной копии. Результаты фактически выполненных проверок и ограничения среды указаны в [verification.md](verification.md).
