# Руководство разработчика ChronoCampus

Документ для участника, который подключается к разработке существующей системы. Состояние реализации: `7e12b5e`, 24 октября 2026. Установка и команды запуска находятся в [README](../README.md); здесь описаны точки входа и правила изменения кода.

## С чего начать

1. Прочитать [правила вуза](requirements.md): подтверждённые требования отделены от демонстрационных настроек и неизвестных значений.
2. Поднять свою локальную БД и приложения по [README](../README.md). Применить миграции, создать администратора или выполнить демонстрационное заполнение.
3. Пройти сценарий: справочники → календарь и учебные периоды → нагрузка → черновик → генерация → проверка и правки → публикация → расписание пользователя.
4. Посмотреть [архитектуру](architecture.md) и [результаты проверок](verification.md), затем открыть нужный модуль из таблицы ниже.

Демонстрационные пароли каждого окружения создаются локально и лежат в игнорируемом `backend/.demo-credentials.json`. Для собственного администратора есть команда `app.manage create-admin`. Устаревшие данные входа из прототипа не являются учётными записями новой системы.

## Как проходят данные

Браузер обращается к `/api` через общий клиент с cookie-сессией и CSRF-токеном. FastAPI проверяет роль, входную схему и предметные ограничения, затем работает с SQL Server через SQLAlchemy. Описание HTTP-контрактов формируется из приложения: [Swagger UI](http://localhost:8000/docs), [OpenAPI JSON](http://localhost:8000/openapi.json). Для новых запросов сверяйтесь с ними и серверной схемой.

Основные связи данных:

- Факультет → специальность → набор одного года поступления → подгруппа → лабораторная подгруппа.
- Семестр → учебные периоды; компонент нагрузки связывает семестр, предмет, участников, преподавателя, вид занятия и часы.
- Компонент нагрузки → конкретные занятия со стабильными идентификаторами; версия расписания хранит их назначения по датам, парам и аудиториям.
- Публикация выбирает доступную пользователям версию для набора. Личная заметка ссылается на конкретное занятие, поэтому сохраняется при переносе его даты.

Генерация проходит через четыре разных ответственности:

1. [snapshot.py](../backend/app/scheduling/snapshot.py) фиксирует исходные данные, версии, закрепления и внешнюю опубликованную занятость.
2. [solver.py](../backend/app/scheduling/solver.py) строит допустимые варианты, получает начальное решение жадным/локальным поиском и улучшает его CP-SAT.
3. [validation.py](../backend/app/scheduling/validation.py) независимо проверяет результат и баланс часов. Эта проверка применяется также при правках и публикации.
4. [router.py](../backend/app/scheduling/router.py) управляет заданиями и сохранением. Устаревший результат не перезаписывает изменённый черновик; публикация проверяется внутри транзакции с блокировкой ревизии БД.

## Как вносить изменения

### Новый параметр или справочник

Сначала определить, относится ли значение к настройкам вуза, календарю, семестру или компоненту нагрузки. Не добавлять реальные правила университета как константы интерфейса.

При изменении хранения обновить модель и добавить следующую миграцию в [backend/alembic/versions](../backend/alembic/versions/). Применённые миграции `0001` и `0002` не переписывать. Их определения схемы зафиксированы и не должны зависеть от будущих изменений ORM-моделей. Проверять миграцию на пустой БД и на восстановленной копии прежней схемы; исходную БД сохранять отдельно. Архивный `db/ChronoCampus.sql` удаляет и создаёт БД заново и не используется для обновления данных.

Затем изменить Pydantic-схему, регистрацию ресурса и предметную проверку в `academics`, соответствующие поля `catalogSchema.ts`, подписи на трёх языках и тесты. Связи, вместимость, доступ и допустимость значений проверяет сервер, даже если форма уже ограничивает ввод.

### Новое правило расписания

Указать, является ли оно обязательным запретом или мягким пожеланием, и записать согласованное поведение в [requirements.md](requirements.md). Проверить влияние на общие календарные функции, снимок входных данных, кандидаты решателя, независимый валидатор и диагностику.

Для жёсткого правила проверить три пути: автоматическую генерацию, ручную правку и публикацию. Учесть закреплённые занятия и опубликованную занятость наборов вне текущего выбора. Для мягкого правила сохранить приоритет полноты, затем окон студентов и равномерности нагрузки; штраф не должен разрешать нарушение жёсткого ограничения.

Изменения данных, влияющих на генерацию, должны участвовать в механизме ревизий. Использовать существующую транзакционную схему из `academics`/`scheduling` и `lock_revision`; не держать блокировку БД во время поиска решения.

### Экран или действие пользователя

Работать в активном `frontend/src/system`, использовать общий `api.ts`, обработку ошибок и диалоги из [common.tsx](../frontend/src/system/common.tsx). Новые подписи и коды ошибок добавлять для RU/HY/EN. Введённые пользователем названия предметов и факультетов не переводятся автоматически.

Защиту нового действия добавить на сервере и проверить под неподходящей ролью; скрытая кнопка не ограничивает доступ к API. Запросы на запись должны сохранять существующую CSRF-защиту.

## Что проверять перед коммитом

Команды установки, pytest, typecheck и сборки приведены в [README](../README.md). Подбирать проверки по изменённому поведению:

| Изменение | Основные тесты |
| --- | --- |
| Учётные записи, роли, пароли | [test_accounts.py](../backend/tests/test_accounts.py) |
| Формы, связи и предметные ограничения справочников | [test_catalogs.py](../backend/tests/test_catalogs.py) |
| Время, часы, ограничения и решатель | [test_scheduling.py](../backend/tests/test_scheduling.py) |
| Полный цикл, переносы, заметки и обращения | [test_workflow.py](../backend/tests/test_workflow.py) |
| Конкурентная публикация на SQL Server | [test_sqlserver_publication.py](../backend/tests/test_sqlserver_publication.py), отдельная тестовая БД |

Обычные тесты используют изолированную SQLite БД и не подтверждают все особенности SQL Server. Для изменений транзакций и миграций нужен реальный SQL Server. Не обходить защиту запуска в [conftest.py](../backend/tests/conftest.py): она не позволяет тестам восстанавливать задания в рабочей БД разработчика.

После изменений интерфейса выполнять typecheck и build, затем проходить затронутый сценарий в браузере, включая нужные роли, языки и узкий экран. `/api/health` подтверждает работу процесса, но не подключение к БД. В [verification.md](verification.md) фиксировать реально проведённые проверки с датой и ограничениями, а не переносить старый результат на новый код.

## Границы, которые важно сохранить

- Обычные учебные периоды задаются отдельно от границ семестра: январь/июнь не становятся учебными месяцами автоматически.
- Дополнительная пара требует явного разрешения администратора. Праздничная отмена и чрезвычайная отработка имеют разные правила учёта часов.
- Опубликованную версию не редактируют; изменения готовят в следующем черновике. Изменение справочников может потребовать новой публикации.
- Стабильные идентификаторы занятий нельзя заменять при переносе. Изменение уже материализованной нагрузки сейчас ограничено; будущая смена учебного плана потребует отдельного механизма версий.
- Поддерживается один процесс API с одним фоновым исполнителем генерации. Дополнительные `uvicorn --workers` требуют предварительного изменения очереди и восстановления заданий.
- `MAIL_MODE=file` сохраняет письмо локально. Университетский SMTP и публичный HTTPS требуют отдельной настройки и проверки; это не подтверждается локальными тестами.

Полный перечень оставшихся ограничений — в [verification.md](verification.md); происхождение демонстрационных данных — в [demo-data.md](demo-data.md).

## Передача работы команде

Следовать [репозиторному workflow](../skills/repo-workflow/SKILL.md): собственная ветка, проверка интеграции с локальным `main`, коммит только относящихся к задаче файлов. Локальный коммит сам по себе не появляется у остальных участников: для этого ветка должна быть опубликована в общем репозитории, после чего оформляется PR в `main`.

В описании изменения указывать поведение, затронутые модули, миграции/настройки и проверки. `.env`, пароли, резервные копии, локальные письма и артефакты запуска не коммитить. Фиксированные пароли для всей команды не нужны: каждый участник создаёт свои локальные аккаунты. Историю этого этапа см. в [описании вклада](contributions.md).
